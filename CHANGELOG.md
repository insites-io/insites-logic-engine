# Changelog

All notable changes to the Insites Logic Engine will be documented in this file.

## [Unreleased]

### New Feature
- **What to build with live updates, multipart uploads and the log query** (`websockets/README.md`, `api-calls/api.md`, `graphql/api.md`, `SKILL.md`, TW#26892599). `websockets/README.md` opens with the uses (AI answers, job progress, live dashboards, record changes, notifications, chat), which code sends each message, how to scope the room, and when to use Server-Sent Events rather than the WebSocket. `form_data` on `api_call_send` and the `admin_logs` query are now measured on a v6 production instance (15 October 2026), with what each is for: reading documents with AI or OCR, attaching files to other systems, sending generated files; a support view of errors, alerts from a scheduled job, a job's own log. The `admin_logs` entry records the full request URL, query string included. The skill's routing tree points at all three.
- **Server-Sent Events work on Insites instances** (`websockets/README.md`, `websockets/patterns.md`, `platform-changes-2026.md`, TW#26892599). At 18:41 (UTC+7) on 15 October 2026 `/anycable-events` began answering on both Insites stacks. Measured end to end on a v6 production and a v6 staging instance: `welcome`, `confirm_subscription`, then a background job's message as a bare payload 4.6 s after subscribing; a refused room and a channel with no `subscribed` partial answer 400, no session or token 401. The README section now documents SSE as available, with the differences from the WebSocket and a one-request check, and the patterns page records the SSE-first page connecting over SSE.

### Bug Fix
- **When several policies fail, the policy created first decides the redirect** (`modules/cms/gotchas.md` item 11, `modules/cms/patterns.md`, `building-on-insites/04-authorization.md`, TW#26876514). The pages said policies run in the order the page lists them and the first failure wins. Measured on one v6 staging instance on 15 October 2026 with three always-failing policies: a page listing `fail_a, fail_b` and one listing `fail_b, fail_a` both went to `fail_a`'s redirect, and `fail_b, fail_0` went to `fail_b`'s, so neither list position nor name decides; the lower id, the policy created first, does. app-seedling's `/dashboard` did the same with its own two policies. The gotcha now gives the safe pattern: make each `redirect_to` right on its own by checking `context.current_user` inside it.
- **There is no `sign_out` tag** (`authentication/api.md`, `authentication/configuration.md`, `authentication/patterns.md`, TW#26876514). Measured on a v6 staging instance on 15 October 2026: `{% sign_out %}` fails with `Unknown tag 'sign_out'`, and the CLI's tag reference lists `sign_in` but no `sign_out`. The three pages now sign out with the `user_session_destroy` mutation, as the v6 CRM module does, and say the schema marks it deprecated ("Use session tag").
- **`{{ }}` output is not HTML-escaped** (`liquid/tags/api.md`, `liquid/tags/gotchas.md`, TW#26876514). The escaping summary said `{{ var }}` is escaped and safe for untrusted input. Measured on a v6 staging instance on 15 October 2026 in a headless browser: `value="{{ x | escape }}"` and `alt="{{ x | escape }}"` were both broken out of by a value holding a double quote, and the second ran an injected `onerror`, while an unescaped `"><img ...>` produced no element. A value escaped into a variable and written with `{% print %}` stayed inside its attribute for two stored values. A new gotcha gives that pattern, and the summary table is corrected.
- **Security: `{{ }}` sanitizes, it does not escape, and the flag that decides it is documented** (`configuration/README.md`, `liquid/tags/{api,gotchas,advanced}.md`, TW#26894310). `escape_output_instead_of_sanitize` read `false` on two v6 instances created in late September 2026, and the v6 system-pages module ships it `false`; with it `false`, `{{ '<b>x&y</b>' }}` was served as `<b>x&amp;y</b>`, the tag kept. `advanced.md` labelled a bare `{{ user.bio }}` safe for user input; it now escapes into a variable and prints it, and the escaping summary says `{{ }}` is not for untrusted text between tags either.
- **No `push`, `unshift`, `pop` or `shift` on v6** (`liquid/types/{api,configuration,patterns,advanced}.md`, `flash-messages/advanced.md`, `sessions/{patterns,advanced}.md`, `assets/advanced.md`, TW#26894310). `push` answers "undefined filter" on v6, and the CLI's filter reference (216 filters) has none of the four. Every example now uses `array_add`, `array_prepend` or `array_delete_at`. The assets example also piped `asset_url` after `push`, which applied it to the array; it now builds the URL first.
- **`redirect_to` takes one value** (`liquid/tags/{api,patterns}.md`, `api/calling-from-liquid.md`, `pages/{patterns,advanced}.md`, `authentication/{api,patterns}.md`, `routing/{api,advanced,patterns}.md`, TW#26894310). A filter chain after it was dropped with no error (measured on a v6 production instance on 8 October 2026), so six examples redirected to an unfinished URL. They now assign the URL and redirect to the variable. Six more put `{{ }}` inside a double-quoted argument, which only renders with `string_interpolation` on; they build the URL first too. The two sign-in guards now `url_encode` the path they pass as `return_to`.
- **A filtered `records_update_all` with `sync: true` is a compare-and-swap** (`graphql/gotchas.md`, `authentication/patterns.md`, TW#26894310). Measured on a v6 production and a v6 staging instance on 15 October 2026: 16 concurrent conditional updates gave exactly one `count` of 1 in each of 24 rounds; without `sync: true`, all 16 won one round. The pages said it never was one.
- **`string_interpolation` and `liquid_raise_mode` are not on by default** (`configuration/README.md`, `liquid/types/{api,configuration}.md`, `liquid/filters/gotchas.md`, `platform-changes-2026.md`, TW#26894310). Two v6 instances created in late September 2026 have no `string_interpolation` flag (a double-quoted `{{ n }}` rendered literally) and `liquid_raise_mode` reads `false`. The pages now say both are per-instance and to set `liquid_raise_mode: true`, and `types/configuration.md` no longer says strings never interpolate while `types/api.md` says double-quoted ones can.
- **Assets: `url` is optional and `cache_control` exists** (`graphql/api.md`, `platform-changes-2026.md`, TW#26894310). Introspected on a v6 production and a v6 staging instance on 15 October 2026: `AssetInput` and `AssetUpdateInput` take `cache_control`, served as the asset's `Cache-Control` header, and `AssetInput.url` is optional, stored as given or built from the name. The bundled `schema.json` predates the 14 October release and still shows `url: String!`; the pages say so.
- **`insites-cli pull` is not a backup** (`cli/api.md`, TW#26894310). It said `pull` exports app data and gave `-p ./backup.zip` as the example. It downloads the `app/` code folder only (16 files from an instance holding about 13,000 records, 25 modules and 126 assets, 27 September 2026), as `cli/advanced.md` already said. The page now says so, uses `app.zip`, and points to `data export` for a backup.
- **Signing out** (`authentication/api.md`, TW#26894310). The page now also says the `session` tag reference documents no way to end a sign-in, so `user_session_destroy`, deprecated with "Use session tag", is still the measured way to sign out.
- **The sign-in code key is `SIGN_IN_HMAC_KEY`** (`authentication/patterns.md`, TW#26876513). The recipe read `context.constants.SIGNIN_HMAC_KEY`, while app-seedling 2.1.0 and the docs' Passwordless Sign-In guide use `SIGN_IN_HMAC_KEY`. Code taken from the recipe and code taken from Seedling or the guide read two different constants. Both mentions now use `SIGN_IN_HMAC_KEY`.
- **A page is not held to a 5-second call, and the timeout is between bytes** (`api-calls/README.md`, TW#26888003). The page said a call from a web request has a default and maximum timeout of 5 seconds, quoting the schema. Measured on 14 October 2026 on a v6 production and a v6 staging instance, a page accepted `timeout: 30` and returned a 7-second call, and with no timeout returned a 10-second one. `timeout` is the longest wait for the next bytes (8 bytes one a second passed `timeout: 5`; 2 bytes 10 s apart failed), a timed-out call fails after about twice its timeout, values outside 1 to 180 are refused, and the edge answers 504 once a page runs past about 20 seconds. The page now carries the table and still says not to build on more than 5 seconds from a page.
- **"Streaming" headings that described paging** (`api-calls/advanced.md`, `pages/advanced.md`). Neither `api_call_send` nor a page streams; the sections fetch or render a batch at a time and are renamed to say so.
- **Why Server-Sent Events are not available, and when the 6 and 14 October releases arrived** (`websockets/README.md`, `platform-changes-2026.md`, TW#26892599). Both releases reached Insites v6 production and staging instances on 15 October 2026, and `/anycable-events` still answers with the instance's 404 page. The cause is measured: that address is served by the stack's real-time server, which reports version 1.2.3 on both Insites stacks, and SSE arrived in 1.4.4. Run locally, 1.2.3 refuses the SSE option and 1.6.16 delivers a broadcast to the release note's `EventSource` code. Later that evening both stacks moved to 1.6.16 and the WebSocket kept working; `/anycable-events` still 404s until SSE is switched on and routed. The page says how to check an instance with one request. `platform-changes-2026.md` now marks 6 October live except SSE and adds the 14 October release.
- **The `_rc` GraphQL names are deprecated and hidden from a default schema read** (`platform-changes-2026.md`, `building-on-insites/05-storing-data.md`). After the 14 October release, `documents`, `records_create`, `records_count` and nine more have stable names; the `_rc` names stay, marked deprecated, and only appear with `includeDeprecated: true`.
- **The new `options.timeout` description** (`api-calls/README.md`). The schema text no longer says "max 5s"; it now says a web request is capped at a shorter timeout than a job. Re-measured after the release, the table is unchanged.
- **The reference apps are no longer cited as following rules they break** (`logic-engine/rules/{pages,forms}.md`, `index.json`, audit batches 1 and 2, TW#26881789). Counted over every file on master on 13 October 2026: no page in app-seedling, app-portal, addon-ecommerce or addon-events declares two methods, but 68 of 110 declare none (app-seedling 16 of 20), so `pages-one-http-method` no longer claims 100% compliance. `{% form %}` appears 27 times in those repos (app-seedling 8), not 4: the earlier count missed `{%- form`.
- **No agency name in a public document** (`SKILL.md`, `forms/README.md`, `pages/README.md`, `partials/patterns.md`, `graphql/gotchas.md`). Mentions of one agency's projects now read as the Insites reference apps, `app-portal` and `app-seedling`, and the GraphQL measurements name "a v6 production instance". The internal working note `logic-engine/audit/skill-update-recommendations.md` is removed; nothing linked to it.
- **`lib/` is optional, not forbidden** (`project-structure.md`, `SKILL.md`, `forms/README.md`, `partials/patterns.md`, `logic-engine/rules/commands.md`). Pages said `app/lib/commands/` and `app/lib/validations/` do not exist while `commands.md` recommended them. insites-cli 6.1.0 treats `lib/` as a partial root, and the v6 CRM module ships `lib/commands/execute` and `lib/validations/{presence,truthy,date_range}`; the reference apps keep state changes in form `callback_actions`. Both are now described as valid.
- **A safe build does not repair an unsafe caller** (`logic-engine/rules/commands.md`, `decisions/feature-pattern/auth-login-flow.json`). app-seedling's `pages/account/2fa.liquid` builds its object with `"otp_code": "{{ otp_code }}"` from the request before the compliant `verify_otp/build.liquid` runs, so it is no longer a login-flow reference, and the rule now says to take identity from `context.current_user` and to prefer an `assign` hash literal. 42 JSON lines across `api-calls/`, `routing/`, `forms/advanced.md`, `liquid/filters/patterns.md` and others wrapped a variable in quotes without `| json`; each now pipes it through `| json`, and three request parameters used as numbers gain `| plus: 0`. `escape_json`, which is not in the insites-cli 6.1.0 filter reference, is gone.
- **The `{% form %}` tag is described the same way everywhere** (`forms/gotchas.md`, `liquid/tags/configuration.md`, `modules/cms/metadata.md`). One page said Insites has no such tag and another called it legacy. It is current and renders a form definition inside `forms/<name>.liquid`; plain `<form>` in pages and partials is the convention.
- **Global Content and `export`** (`liquid/tags/{api,advanced}.md`, `liquid/variables/{api,gotchas}.md`, `liquid/objects/{api,configuration}.md`, `modules/cms/{patterns,metadata}.md`). `modules/insites_cms/get_globals` does not exist: the v6 CMS module's `globals` partial ends `{% export global %}`, read as `context.exports.global` after `{% include 'modules/insites_cms/globals' %}`. `export` takes variable names and a `namespace`, not `export x = y`, and creates no variables in the caller; `return` does not write to `context.exports`; GraphQL results are not exported. `context.current_user` is current, not deprecated, and `context.environment` is a string with no properties.
- **`modules pull` writes a zip** (`cli/{api,advanced,patterns,README}.md`). insites-cli 6.1.0 saves `modules.zip` (or the `-p` path) and does not unpack it, so the examples unzip it. Argument order and `sync` watching already matched 6.1.0.
- **Rate limits count in a table** (`authentication/advanced.md`, `sessions/advanced.md`). The session counter and the read-then-increment counter are replaced by a pointer to the measured pattern.
- **Configuration** (`configuration/{README,configuration,api}.md`, `logic-engine/rules/modules.md`). `liquid_check_mode` and `graphql_argument_type_mismatch_mode` join the flat flags; nested `app/config.yml` sections and `context.config` are marked unverified; a root `app.yml` is a repository description that the CLI never reads.

### Improvement
- **Server-Sent Events first, WebSocket fallback** (`websockets/patterns.md`, TW#26892599). A version of the recipe's script that opens an `EventSource` and falls back to the WebSocket when the stream errors before `confirm_subscription`, so a page switches to SSE by itself once the stack serves it. Run on a v6 production instance (fell back, answer in 10.1 s) and locally against a real-time server that serves SSE (delivered over SSE).
- **A policy's `redirect_to` is Liquid, and the platform adds `return_to`** (`modules/cms/metadata.md`, TW#26876514). Measured on a v6 staging instance on 15 October 2026: `redirect_to` rendered `{% if context.current_user %}` and `{{ context.location.pathname | url_encode }}`, and the platform appended `return_to=<path and query>`, URL-encoded, after any query the value already had (`?rt=...&return_to=...`).
- **A `format: json` page answers 404 to some `Accept` headers** (`pages/gotchas.md`, `routing/advanced.md`, TW#26876514). Measured with `curl` on a v6 staging instance on 15 October 2026: `*/*` and `application/json` got 200; `application/json, text/plain, */*` (axios's default), `text/html` and no `Accept` header got 404. app-seedling's e2e tests failed 5 of 5 with 404 until they sent `Accept: application/json`.
- **A module controller answers only to its path alias** (`api/calling-from-liquid.md`, TW#26876514). Measured on a v6 staging instance on 15 October 2026: the CRM event stream controller by its file path, `modules/insites_crm/controllers/_external/v2/_globals/event_stream/get_event_streams`, failed with `can't find partial`, and by its alias, `crm/controller/event-streams/list`, it answered. The page also says how to quiet the linter's `MissingPartial` on an alias.
- **Sending from the instance's verified sender** (`emails-sms/configuration.md`, `emails-sms/gotchas.md`, TW#26876514). `modules/insites_crm/functions/email_sender/resolve` and `customer_sender` were documented nowhere. The configuration page now says what they return (read from module-v6-crm v6.1.4, and marked internal) and how app-seedling 2.1.0 uses them: send from the verified sender, with `company_name` from CMS Globals as the display name and `company_email_1` as Reply-To, because a customer domain that is not verified fails SPF, DKIM and DMARC. Measured on a v6 staging instance on 15 October 2026 from the sent-email log, with and without Globals. The Reply-To gotcha no longer says the Reply-To must match the sender's domain.
- **`sign_in` rotates the session cookie** (`authentication/api.md`, `authentication/patterns.md`, TW#26876513). Measured on an instance on 15 October 2026: `_insites_session_id` changes on the request that signs the user in, for password, code and link sign-in, and the pre-sign-in cookie is not signed in. Session fixation is not possible, so the recipe needs no step of its own for it.
- **WebSockets** (`websockets/README.md`, `websockets/patterns.md`, `SKILL.md`, `configuration/README.md`, TW#26888003). The first reference for channels, measured on a v6 production and a v6 staging instance on 14 October 2026: the socket URL and the token it must carry, the subscribe conversation, what a `subscribed` partial outputs to admit or refuse, that it can read `context.constants` but not `context.session` (and not `context.current_user` for a visitor), and `channel_send_message` from a background job. `patterns.md` is a six-file recipe for the case that needs it most, a slow API call made from a job and pushed to the browser, with rooms signed by HMAC so `subscribed` admits only rooms the instance issued. Run as written in a headless browser: the reply arrived 9.6 s after submit, and forged and unsigned rooms were refused.
- **Password reset by emailed link** (`authentication/patterns.md`, `authentication/advanced.md`, `authentication/api.md`, TW#26881789). A full recipe on the platform's `temporary_token`, run as written on a v6 production instance on 13 October 2026 with eight of eight cases passing. `api.md` documents `temporary_token` with what was measured: hours as a Float, a readable `id|expiry` payload under a signature, no use-up on opening, every earlier token ended by a password change, and a 0.01-hour token refused after 36 seconds. The old five-line outline in `advanced.md` now points at it. It says to decide who may reset, since every CRM contact is a user record.
- **Open redirects** (`routing/gotchas.md`): `redirect_to` follows full and protocol-relative URLs, measured on a v6 staging instance; a same-site path check that passed 12 of 12 cases. Four examples that redirected to `context.params.return_url` unchecked now point at it.
- **Short sections grounded in the schema or module source**: two-factor codes (`otp`, `authenticate { otp_code }`, `user_otp_secret_refresh`) in `authentication/api.md`; session state versus profile state in `sessions/README.md`; `resource_owner` and its pairing with `authorization_policies` in `forms/README.md`; whole-page caching (`dynamic_cache`, `static_cache_expire`) and invalidation on deploy in `caching/`.

### Bug Fix

- **`context.headers` is keyed the CGI way, and bracket reads by HTTP name return blank.** A header's name is uppercased, hyphens become underscores, and `HTTP_` is prefixed (`X-Api-Key` → `HTTP_X_API_KEY`). The references documented `context.headers['User-Agent']` as case-insensitive in 22 places across 7 files, including the Stripe webhook example; every one of those reads returns blank. Measured on two instances with a read-only probe. All examples now use the dot form, and the rule is stated once in `liquid/objects/README.md`.
- **The endpoint examples named a policy that does not exist.** `api-endpoints/README.md` and `crm-controllers/README.md` used `is_api_authenticated`, which no module ships. They now use `modules/insites_core/has_valid_instance_api_authorization`.
- **Endpoint auth documented as it ships.** The CRM V2 endpoints moved from a front-matter policy to an inline `api_key_guard` function in May 2026 (TW#26083226), because a failed policy answers with a 302 redirect rather than a 401. `api/authentication.md`, `api/calling-from-liquid.md`, `api-endpoints/README.md` and `building-on-insites/04-authorization.md` now describe both guards and how each fails.
- **`auth-policy-explicit-true-false` states what was measured.** Whitespace around `true` is trimmed, and blank output currently fails closed. The rule stands, and now records that 12 of 31 module policy files rely on blank meaning deny.
- **`max_deep_level` was described four different ways, and none matched the platform schema.** Pages called it a recursive-partial limit, the CMS reference called it a GraphQL query depth, and two limits tables tied it to render and partial nesting. The schema defines it as the URL nesting a slug resolves. Measured on a live instance, it did not cap that either. All four now point at one explanation (`routing/gotchas.md`).
- **Crypto filters corrected.** There is no `hmac_sha256` filter on Insites: it answers "undefined filter" on v5 and v6 instances alike. Eight examples and two reference entries used it. The three webhook signature checks built from them refuse every correctly signed request: a page built the same way did exactly that on a v6 instance. They now use `compute_hmac`, which exists and returns HMAC-SHA256 as hex (or base64 with `'sha256', 'base64'`). The `md5` and `sha256` filters do not exist either; the examples now use `digest: 'md5'` and `digest: 'sha256'`.
- **JWT filters corrected.** `jwt_encode` and `jwt_decode` need the algorithm first (`'HS256', secret`); the one-argument form is refused. `jwt_decode` returns `[payload, header]`, not the payload alone.
- **Deletes corrected.** `record_delete` and `records_delete_all` do not remove the row: it is kept with `deleted_at` set, under the same id, and a `deleted_at` filter still returns it. Three pages said deletion is permanent with no soft delete.

### Improvement

Pages that read an id off `context.location.pathname` with `extract_url_params` break when the flag is on. The fix is a `:param` in the slug. ## [1.0.0] - 2026-03-19

### What is this?

Insites AI Tools is a skill documentation package that teaches LLMs (Claude, GPT, etc.) how to write correct code for the Insites platform. When installed, AI assistants can help developers build pages, query data, create commands, handle authentication, deploy code, and follow Insites coding conventions — without hallucinating unsupported features.

### Key Features

- **Liquid Templating** — Complete reference for Insites-specific tags (`graphql`, `function`, `render`, `background`, `cache`, `session`, `sign_in`, etc.), filters, objects, and coding standards including whitespace stripping guidance
- **GraphQL Data Layer** — Queries, mutations, property accessors, relationships (`related_record` / `related_records`), filtering, sorting, and pagination patterns
- **Command Pattern** — Build → Check → Execute workflow with inline validation, contract-based error accumulation, and 16 documented validation patterns (presence, uniqueness, number, email, length, format, date, and more)
- **Authentication & Authorization** — `authorization_policies/` for page guards, `context.current_user` for user access, role-based permission checking, sign-in/sign-out flows
- **Routing** — File-based routing with dynamic parameters, content-type mapping, HTTP method handling, and slug configuration
- **Schema & Migrations** — YAML schema definitions, property types, relationship conventions, migration lifecycle, and deployment
- **Events & Background Jobs** — Asynchronous event consumers, background job dispatch with `{% background %}` tag, priority and retry configuration
- **Sessions, Caching, Flash Messages** — Native session management via `context.session`, cache tag patterns, flash message flows with redirect
- **Module Development** — `public/` vs `private/` path conventions for building reusable modules
- **Code Refactoring Guide** — When and how to extract reusable partials (validations, execute helpers, UI components, authorization policies) with before/after examples
- **CLI Reference** — All `insites-cli` commands (`audit`, `deploy`, `sync`, `logsv2`, `env add`, `gui serve`, `migrations`, `modules`, `data`) with correct syntax and status notices on under-development commands
- **Decision Trees** — Deterministic routing from any developer request to the correct reference docs
