# Changelog

All notable changes to the Insites Logic Engine will be documented in this file.

## [Unreleased]

### Improvement

- **Passwordless sign-in as a full recipe** (`authentication/patterns.md`, `graphql/gotchas.md`, TW#26872247, 9 October 2026). The "Sign-in by emailed link" section is now "Sign-in by emailed link or code": what both variants share (same answer for every address, limits counted on every row, a session flag on every POST, mail through a registered template), shared `client_ip` and `take_slot` partials, and a six-digit code variant with its table, `compute_hmac` code hash, request and verify pages and email, run on a production instance with nine of nine cases passing. The link variant gains the check query and the consume step. Measured along the way and now documented: a read-then-write counter let 14 of 16 concurrent wrong guesses through a limit of 5 and let two right codes both sign in, and `increment: 1` also let two through, while one row per slot with a unique `external_id` let exactly one through every time; a property written with `value` is text, so `value_int` filters miss it; a number passed as `value` fails the mutation with no exception; a POST without a valid token arrives with an empty session.

### Bug Fix

- **No upstream vendor names, hosts or borrowed APIs** (`flash-messages/*`, `layouts/*`, `partials/patterns.md`, `forms/README.md`, `modules/{api,assets,data,ecommerce,events,locator,permissions,pipelines}/*`, `building-on-insites/reference/crm-contacts-list.md`, `graphql/schema/schema.json`, `skills_examples/{insites-auth,insites-unit-tests}`, `README.md`, the audit notes, TW#26872247). Module source paths read `modules/<name>/` in the module repository. Links to outside documentation now point at docs.insites.io or this repository. `INSITES_POS_KEY` and the `pos_login` response key keep their names because insites-cli 5.10.2 ships them.
- **The visitor's address is `X-Real-IP` or the first `X-Forwarded-For` entry** (`liquid/objects/{gotchas,README,api,configuration}.md`, `authentication/patterns.md`, TW#26872247). 2.0.0 said to read the last hop, and the objects gotchas used the first while calling the header spoofable. Measured on a production and a staging instance on 9 October 2026: the edge replaces a client-sent `X-Forwarded-For` and `X-Real-IP`, the first entry equals `X-Real-IP`, and the last is an internal proxy address that changes per request. Forged `Client-IP` and `CF-Connecting-IP` get a 403; forged `True-Client-IP` and `Forwarded` pass through and must not be trusted. `context.visitor.ip` is listed in the CLI object reference but was not measured, and the GeoIP fields the pages listed are not in that reference.
- **The CLI pages match CLI 5.10.2** (`caching/*`, `constants/README.md`, `cli/{README,api,advanced,patterns,gotchas}.md`, `deployment/{api,advanced,patterns,configuration}.md`, `api-calls/*`, `modules/template/configuration.md`, TW#26872247). There is no `insites-cli cache` command, so the cache pages now invalidate by key. `insites-cli constants` ships, and every `constants set` example uses `--name` and `--value`. `gui serve` takes `-p, --port` (default 3030). `data import` reads JSON, or a zip with `--zip`, and takes no table argument; `data export` writes a zip; `data clean` removes all data, not one table. `insites-cli audit` exits 0, so the CI examples now gate on its `[Audit] 0 rules detected issues.` line instead of `|| exit 1`.
- **GraphQL and schema corrections** (`emails-sms/*`, `schema/{api,README,configuration,patterns,advanced}.md`, `graphql/{api,patterns}.md`, `building-on-insites/05-storing-data.md`, `user-profile-types/README.md`, `platform-changes-2026.md`, `logic-engine/templates/graphql-crud.eta`, TW#26872247). `email_send` and `sms_send` take `template: { name: ... }` and a `data` variable and answer `is_scheduled_to_send`; the invented `to:`, `success`, attachment and status examples are gone. `record_delete` examples pass `table`, which a v6 instance required and 107 of 108 v6 module calls pass. Examples use `type: string`, since `text` is deprecated in the schema. `admin_assets_create` now says only what the schema and the release notes agree on: send `url`, do not rely on its value.
- **`graphql-tables-fully-qualified` is narrowed** (`logic-engine/rules/graphql.md`, `index.json`). Module tables carry `modules/{module}/`; a table in `app/schema/` is named by its file name, which worked for every query and mutation in the passwordless build.
- **Liquid corrections** (`liquid/flow-control/{api,configuration,gotchas,README}.md`, `liquid/types/api.md`, `liquid/filters/{api,patterns,advanced,README}.md`, `liquid/tags/api.md`, `logic-engine/rules/forms.md`, `engine/src/validators.ts`, TW#26872247). `and` and `or` have no precedence and group from the right (`a and b or c` is `a and (b or c)`), as the Liquid `if` tag source builds it; five pages said `and` binds first or that chains run left to right. `time_diff` returns milliseconds unless given a unit, per the filter reference shipped with CLI 5.10.2, so the examples dividing by 3600 or 86400 were 1000 times too large. `{% form %}` is not deprecated (the CLI tag reference marks it current and the v6 CRM module uses it); `forms-no-form-tag` stays as a convention and its message no longer says deprecated. `render_form` stays an alternative spelling, with a note that the CLI audit still lists it as deprecated.
- **`app/` and `modules/` are both valid layouts** (`SKILL.md` Project Structure, `project-structure.md`, `pages/README.md`, the partials, GraphQL and layouts configuration pages, `liquid/tags/gotchas.md`, `deployment/api.md`, `deployment/configuration.md`, TW#26872247, 9 October 2026). The skill said every project is organized by module and there is no top-level `app/`, while its own audit list resolved `render` into `app/views/partials/` and the public Codebase guide documents `app/`. The rule is now stated once, in the same words in both files: `app/` holds the site itself, and `modules/<name>/` holds code you want to reuse or package. A table gives how `render`, `function`, `graphql`, `layout:` and `authorization_policies:` resolve in each tree; a path that starts `modules/<name>/` reads that module's `public/` or `private/` tree, checked against the v6 CRM module source and the CLI's own path resolver. The GraphQL and partials configuration pages said a module path drops the module prefix; it does not, and the layouts page now says so too. `liquid/tags/gotchas.md` marked `render 'partials/header'` as correct; it reads `app/views/partials/partials/header.liquid`. The deploy page listed `config/` among the synced folders; the CLI syncs and deploys `app/` and `modules/` only.
- **The audit list says what `insites-cli audit` checks** (`SKILL.md` section 2, `cli/api.md`, `cli/README.md`, `cli/patterns.md`, `cli/gotchas.md`, `deployment/{README,api,gotchas}.md`, `pages/gotchas.md`, `partials/gotchas.md`, `modules/cms/gotchas.md`, TW#26872247). Read from the CLI 5.10.2 source and run against a fixture. It does not check Liquid syntax, routes, HTML in pages, GraphQL in partials, translations or credentials, though several pages said it did. A lone `_card.liquid` passes, so `partials-no-underscore-prefix` keeps its `real-project` evidence. The orphan check ignores `render` and turns itself off at the first `{% function result = '...' %}`. The conventions the audit does not check now sit in their own list in `SKILL.md`, each named after the Logic Engine rule that holds it.
- **Translations are supported** (`SKILL.md`, `liquid/filters/README.md`, `partials/{README,gotchas,patterns}.md`, `layouts/patterns.md`, `pages/patterns.md`, `flash-messages/{gotchas,configuration}.md`, `cli/gotchas.md`, `deployment/gotchas.md`, TW#26872247). `SKILL.md` said user-facing text is hardcoded in English, and several pages said to use plain English text. The Translation Filter section now covers the files (`app/translations/<locale>.yml`, or a module's `translations/`), the `t` filter with `%{name}` interpolation and `default:`, `context.language`, the `?language=` parameter, `{% context language: %}`, the English fallback and the admin translation mutations, and links the public guide. Three pages placed translations in `config/translations.yml`, which the CLI never deploys.
- **`insites-cli logs` exists and is the live stream** (`cli/{README,api,gotchas,patterns,advanced}.md`, `deployment/{api,gotchas,patterns,advanced}.md`, `background-jobs/*`, `SKILL.md`, `authentication/gotchas.md`, four `skills_examples`, TW#26872247). The CLI README said `logs` does not exist; CLI 5.10.2 registers it (alias `l`). It polls the instance until `Ctrl+C`, takes `--interval`, `--filter <type>` (matched against the entry's type, not its text) and `-q`, and rejects `--follow`, `--tail` and `--source-name`, which the pages used. Because it never exits, the scripts that counted it with `wc -l` or read it with `tail` are gone. `logsv2` takes a subcommand first (`logsv2 staging` is an unknown command), has no `--filter`, ships no script for `alerts rm`, and stops on the Insites stack, where v6 instances run, because that stack publishes no log proxy. It does not print `source_name`, so the background-job pages now log from inside the job with a type to filter on, and the invented `SUCCESS`/`FAILED` log lines are removed. The same pages used `sync --watch`, `--include`, `--filter`, `--verbose` and `--config`, which the CLI rejects; `sync` watches by default, `DEBUG=1` prints debug lines, and `CONFIG_FILE_PATH` picks another `.insites`.
- **GraphQL in a partial is a convention, not a platform limit** (`SKILL.md`, `graphql/{gotchas,configuration}.md`, `partials/{README,patterns,gotchas}.md`, `pages/patterns.md`, `modules/cms/gotchas.md`, `logic-engine/rules/partials.md`, TW#26872247). The pages quoted a "graphql tag is not allowed in partials" error and said partials cannot query; a partial called with `{% function %}` ran an inline mutation on a production instance on 9 October 2026 (`signin/take_slot`). Every page now says what `graphql-in-partials-restricted` says: presentation partials take data as parameters, block, calculation and callback partials may query, and a reusable query goes in a partial called with `function`. The query wrapper pattern now holds a query.
- **CI credentials use the variables the CLI reads** (`deployment/{configuration,gotchas,patterns,advanced,README}.md`, `configuration/{configuration,gotchas}.md`, `cli/configuration.md`, TW#26872247). The token variables and the YAML profiles with `${VAR}` that the pages named were invented. CLI 5.10.2 reads `INSITES_URL`, `INSITES_EMAIL`, `INSITES_TOKEN`, `INSITES_INSTANCE` and `INSITES_POS_KEY`, only when all five are set, and then ignores `.insites` and the environment name. `.insites` is JSON and is not expanded. The install line `npm install -g /insites-cli` is now `@insites/insites-cli`.
- **The email queue example sends through a registered template** (`emails-sms/patterns.md`, TW#26872247). The queue used `model_create`, which the schema marks deprecated ("Use records instead of models"), with a `model_name` field and a `success` answer the schema does not have, and `properties` as an object where the schema takes a list. It is now one `email_send` per recipient, by template name with `data` as one variable, looped in a background job started with `background job_id = '...'`.
- **Declare the `roles` user property before checking it** (`authentication/{configuration,gotchas,api,advanced,patterns,README}.md`, `user-profile-types/README.md`, `deployment/{api,gotchas,configuration}.md`, `project-structure.md`, `skills_examples/insites-auth`, TW#26872247). Measured on a stock instance on 10 October 2026: there is no `roles` property on users, so `property_array(name: "roles")` reads back `[]` and an `array_contains` filter on `roles` returns `GraphQL Error: array_contains only works for arrays, roles is` inside the result, with no Liquid error, and matches nobody. Every role check written as documented therefore failed closed and silently. The property is now declared first in `app/user.yml`, as a `properties:` list (`- name: roles`, `type: array`), and set with `user_update` and `value_array`. The schema's own descriptions name `user.yml` for user properties, and Insites' Console declares its user properties the same way. The deploy pages showed `app/schema/models/user.yml` in a map shape, which is not what worked. An inline array literal passed to the `graphql` tag (`roles: ['member']`) made a deploy fail, while `'member' | split: ','` worked, so the role examples build the list with `split`.
- **Install commands fetch from `master`** (`README.md`, `command/insites.md`, the usage lines in `install.sh`, `claude-install.sh` and `install-examples.sh`, TW#26872247). The repository's default branch is `master` and it has no `main` branch, so every `raw.githubusercontent.com/.../main/...` URL now reads `.../master/...`. All three URLs answer 200.
- **No `config`, `env info` or `env current` command** (`configuration/{api,gotchas,README}.md`, `cli/{advanced,configuration}.md`, `deployment/api.md`, TW#26872247). None exists in CLI 5.10.2, and nor do the deploy options `--force`, `--skip-tests`, `--verbose` and `--dry-run`. The pages now use `insites-cli env list`, `DEBUG=1`, `insites-cli archive` with `insites-cli audit` to check a build without deploying, and the deploy's own `Deploy succeeded after` or `Deploy failed.` line. `deploy` takes `-p` and `--stack`. No environment name runs tests, there is no default environment, and `app/config.yml` holds flat top-level flags with no `modules:` section.
- **Pages may hold simple HTML** (`modules/cms/gotchas.md`, `pages/patterns.md`, TW#26872247). CMS gotcha 2 and the pages best practices still said pages must contain no HTML, against `pages-prefer-partials-for-shared-html`: HTML reused across pages, or composed from three or more blocks, goes in partials, and a simple page keeps its own. CMS gotcha 4 called the `{% form %}` tag unused and said it broke CSRF; it now says the tag is current and plain `<form>` is the `forms-no-form-tag` convention.
- **Background jobs use the partial form and see only what is passed** (`background-jobs/*`, `emails-sms/{README,api,advanced,patterns}.md`, `liquid/tags/{api,configuration,patterns,gotchas,advanced}.md`, TW#26872247). The tag reference shipped with CLI 5.10.2 lists the block form (`{% background %}...{% endbackground %}`) under deprecated and says a job has only the variables passed to the tag, with a limited `context`. The pages used the block form throughout and told readers to reassign page variables inside it, which reads a blank. Every example now names a partial with `background job_id = '...'` and passes what the job needs as arguments. The invented `task:` and `retry:` arguments and the one-minute minimum delay are gone.
- **No upstream vendor modules** (`forms/{README,configuration}.md`, `configuration/README.md`, `layouts/gotchas.md`, `skills_examples/{insites-unit-tests,insites-auth}`, TW#26872247). The `common-styling` upload component is replaced by the presigned upload the v6 modules use (`property_upload_presigned_url`, a browser POST to `upload_url`, then the URL saved on the record). The `core`, `user` and `common-styling` entries in `app/config.yml`, the session-module check, the user module's helper and built-in endpoints, and the `modules/tests/` paths with their `helpers/init` are gone; the unit-test example uses the `insites_test` module bundled with insites-cli, whose runner passes `contract` in. The CLI README and command reference no longer use em dashes.

- **An asset upload does not purge the plain address** (`assets/gotchas.md`, `assets/configuration.md`, TW 26851120, 7 October 2026): the file host caches every asset for a year at the edge and ten years in the browser, and a re-upload left the plain address serving old content on 30 of 30 checks over 15 minutes, on one staging and one production instance, and was still old eight hours later. An operator purge of the exact URL clears the edge within seconds but cannot reach browsers. Only `asset_url`'s `?updated=` address is cache busted. Two claims are corrected: file names do not get a version hash on deploy, and an edge purge is an operator action rather than a dashboard step (`deployment/gotchas.md`).
- **`context.location.search` is JSON and `href` is the path** (`liquid/objects`): measured on one v6 instance, `search` renders the parsed parameters as JSON and `href` the path with its query, where the references said the opposite. A redirect built from `search` is refused and the page answers 200 with the error (TW#26860023).
- **Measured v6 facts the schema does not state** (`graphql/gotchas.md`): `import_models` with `_id_remap` answers ids in the order sent, echoes `external_ids`, preserves `created_at` and `updated_at`, stores the model's `id` as the external id, and makes a second copy of every row when sent twice, so a lost answer is read back by external id rather than resent. Names belong in variables, not query text. `admin_table_delete` takes a path. The admin API lists only a module's public partials and layouts. A policy's `http_status` has no input field. `constants` answers one page of 1000 and must be paged. All measured on a v6 instance between 28 September and 6 October 2026 (TW#26848218).
- **`updated_at` is a stamp, not a change log; a deleted row's id stays reserved** (`schema/gotchas.md`). An import that clears a property leaves the stamp alone, two edits in a second share it, and a table whose rows were all deleted drops out of the listing. A row re-imported under a deleted id comes back under a new id.
- **`hook_module_info`'s version lags the tag** (`modules/cms/advanced.md`, `modules/crm/advanced.md`). Release tooling does not bump it: five modules read 6.0.0 while tagged v6.0.2 on 5 October 2026. The hook answers "installed", the git tag answers "which version". The CRM entry also records that `insites_core` is retired on v6 in favor of `insites_crm`, and what a v6 instance with both installed means.
- **Sign-in by emailed link** (`authentication/patterns.md`): `temporary_token` plus a stored nonce, consumed on a second request because scanners open links first, the same answer for every address, the last `X-Forwarded-For` hop, and accounts made only by a signed server-to-server request. Proven on Nucleus and the Insites Migration Tool.

- **Ten findings from the Squarespace move** (TW 26851116, 5 and 6 October 2026): the authenticity token is masked per render and cannot be compared by a page, the session is the check (`forms/gotchas.md`); asset name and path are both unique and the name decides which record a create updates, `admin_asset_delete` by path can hit an older deleted record and leave the live one, `admin_asset_delete_all` with `hard_delete` is a background job that can stop part way, and the file host keeps serving old bytes at an asset's plain address (`assets/gotchas.md`); `import_users` does not answer its ids in the order sent, so nothing is paired by position, and a list paged without a sort repeats and misses rows (`graphql/gotchas.md`); an upload property can hold an upload, an address or `{}` and each reads differently (`schema/gotchas.md`); `api_call_send` takes an inline request, now documented, and the payments stub's Checkout Session example uses it (`api-calls/README.md`, `payments/README.md`).

- **Carts and checkout are the project's to build** (`payments/README.md`, `building-on-insites/05-storing-data.md`). The Ecommerce module stores carts, cart items and orders; the storefront is built per project, starting from the official `app-portal` and `addon-ecommerce` templates.
- **`admin_asset_delete_all` is documented as current behavior** (`assets/gotchas.md`). Measured on two v6 instances on 7 October 2026: it answers `scheduled` with no job id, works at about 3 to 4 assets a second on staging and 6 to 11 on production, and matches already-deleted assets. A path prefix filter runs as fast as an id filter, which corrects the entry that said a prefix filter does not run. `hard_delete: true` stamps `deleted_at` with the time of the call, the same as a delete without it, so the record and the file stay for the 30 days every deleted item is kept. Completion is read by polling the count (TW#26851122).
- **One word: delete.** Insites does not use "soft delete" or "hard delete". A delete keeps the item for 30 days from its `deleted_at`, then an overnight job removes it (`schema/api.md`, `assets/gotchas.md`, `building-on-insites/05-storing-data.md`). A row's `deleted_at` can be set back to have it removed sooner; an asset's cannot. The CRM and Data module pages now say "delete" and "archive", and the archive pattern in `schema/advanced.md` uses an `archived_at` field (TW#26851122).
- **`admin_asset_delete` by path is documented as current behavior** (`assets/gotchas.md`). Reproduced on 7 October 2026: once a path has been deleted and written again, a delete by that path answers with the old deleted record every time and leaves the live asset. A delete of the old record with `hard_delete: true` does not clear it. The way round it is to read the live id and delete by id, which removed the live copy within seconds. The workaround no longer suggests filtering by path, which also matches the old deleted record (TW#26851118).

### Bug Fix

- **`context.headers` is keyed the CGI way, and bracket reads by HTTP name return blank.** A header's name is uppercased, hyphens become underscores, and `HTTP_` is prefixed (`X-Api-Key` → `HTTP_X_API_KEY`). The references documented `context.headers['User-Agent']` as case-insensitive in 22 places across 7 files, including the Stripe webhook example; every one of those reads returns blank. Measured on two instances with a read-only probe. All examples now use the dot form, and the rule is stated once in `liquid/objects/README.md`.
- **The endpoint examples named a policy that does not exist.** `api-endpoints/README.md` and `crm-controllers/README.md` used `is_api_authenticated`, which no module ships. They now use `modules/insites_core/has_valid_instance_api_authorization`.
- **Endpoint auth documented as it ships.** The CRM V2 endpoints moved from a front-matter policy to an inline `api_key_guard` function in May 2026 (TW#26083226), because a failed policy answers with a 302 redirect rather than a 401. `api/authentication.md`, `api/calling-from-liquid.md`, `api-endpoints/README.md` and `building-on-insites/04-authorization.md` now describe both guards and how each fails.
- **`auth-policy-explicit-true-false` states what was measured.** Whitespace around `true` is trimmed, and blank output currently fails closed. The rule stands, and now records that 12 of 31 module policy files rely on blank meaning deny.
- **`max_deep_level` was described four different ways, and none matched the platform schema.** Pages called it a recursive-partial limit, the CMS reference called it a GraphQL query depth, and two limits tables tied it to render and partial nesting. The schema defines it as the URL nesting a slug resolves. Measured on a live instance, it did not cap that either. All four now point at one explanation (`routing/gotchas.md`).
- **Crypto filters corrected.** There is no `hmac_sha256` filter on Insites: it answers "undefined filter" on v5 and v6 instances alike. Eight examples and two reference entries used it. The three webhook signature checks built from them refuse every correctly signed request: a page built the same way did exactly that on a v6 instance. They now use `compute_hmac`, which exists and returns HMAC-SHA256 as hex (or base64 with `'sha256', 'base64'`). The `md5` and `sha256` filters do not exist either; the examples now use `digest: 'md5'` and `digest: 'sha256'`.
- **JWT filters corrected.** `jwt_encode` and `jwt_decode` need the algorithm first (`'HS256', secret`); the one-argument form is refused. `jwt_decode` returns `[payload, header]`, not the payload alone.
- **Deletes corrected.** `record_delete` and `records_delete_all` do not remove the row: it is kept with `deleted_at` set, under the same id, and a `deleted_at` filter still returns it. Three pages said deletion is permanent with no soft delete.

### Improvement

## [1.0.0] - 2026-03-19

### What is this?

Insites AI Tools is a skill documentation package that teaches LLMs (Claude, GPT, etc.) how to write correct code for the Insites platform. When installed, AI assistants can help developers build pages, query data, create commands, handle authentication, deploy code, and follow Insites coding conventions — without hallucinating unsupported features.

### Key Features

- **Liquid Templating** — Complete reference for Insites-specific tags (`graphql`, `function`, `render`, `background`, `cache`, `session`, `sign_in`, etc.), filters, objects, and coding standards including whitespace stripping guidance
- **GraphQL Data Layer** — Queries, mutations, property accessors, relationships (`related_record` / `related_records`), filtering, sorting, and pagination patterns
- **Command Pattern** — Build → Check → Execute workflow with inline validation, contract-based error accumulation, and 16 documented validation patterns (presence, uniqueness, number, email, length, format, date, and more)
- **Authentication & Authorization** — `authorization_policies/` for page guards, `context.current_user` for user access, role-based permission checking, sign-in/sign-out flows
- **Routing** — File-based routing with dynamic parameters, content-type mapping, HTTP method handling, and slug configuration
- **Schema & Migrations** — YAML schema definitions, property types, relationship conventions, migration lifecycle, and deployment
- **Events & Background Jobs** — Asynchronous event consumers, background job dispatch with `{% background %}` tag, priority and retry configuration
- **Sessions, Caching, Flash Messages** — Native session management via `context.session`, cache tag patterns, flash message flows with redirect
- **Module Development** — `public/` vs `private/` path conventions for building reusable modules
- **Code Refactoring Guide** — When and how to extract reusable partials (validations, execute helpers, UI components, authorization policies) with before/after examples
- **CLI Reference** — All `insites-cli` commands (`audit`, `deploy`, `sync`, `logsv2`, `env add`, `gui serve`, `migrations`, `modules`, `data`) with correct syntax and status notices on under-development commands
- **Decision Trees** — Deterministic routing from any developer request to the correct reference docs
